Pickle 확정 보관·삭제 정책 및 구현 상태
기준일: 2026-10-15 / 동의 버전 2026-10-15.3
운영자: Taelim Auh, 대한민국 / admin@getpickleapp.com

확정 범위
사용자는 계정·레시피·사진을 탈퇴 시 삭제하고, 최소 잔여 처리 기록과 자체 백업만 최대 30일 보관하는 방식을 선택했습니다. 상세 신고 증거는 종결 후 30일, 최소 제재 이력은 90일로 유지합니다. 모든 기간은 이 서비스의 운영 정책이며 모든 나라의 일률적인 법정 기간이라는 뜻은 아닙니다.

1. 계정과 원본 콘텐츠
탈퇴 요청을 받으면 계정 프로필·게시 레시피·댓글/리뷰를 공개 화면에서 숨기고 새 일반 쓰기 및 새 메시지 수신을 제한합니다. 계정·본인 게시 레시피·초안·업로드 아바타/레시피/채팅 사진·대화·저장/좋아요/팔로우/차단 등 연동 자료의 삭제를 즉시 시도합니다.
Storage 파일 삭제를 확인한 뒤 Auth 계정을 삭제하고, 계정 관련 DB 행은 연동 삭제합니다. 다른 대화 참여자가 보낸 해당 대화 사진도 기존 대화 삭제 범위에 포함합니다. 레시피·사진·대화 원본을 탈퇴 복구용 별도 백업에 새로 복사하지 않습니다.
이미 받은 사본/캡처/공개 URL 캐시, 다른 사용자가 독립적으로 게시한 콘텐츠와 외부 서비스의 원본은 앱에서 모두 회수할 수 없습니다.

2. 실패·재시도
요청 접수(accepted)와 삭제 완료(completed)를 구분합니다. 일부 파일 삭제 후 네트워크/인증/DB 문제가 날 수 있고, 완료하지 못한 상태를 삭제 완료라고 표시하지 않습니다.
서버 작업 큐가 단계·대상 파일 경로·시각·시도 수·고정 오류 코드만 보관하며 자동 재시도합니다. 작업 임대 토큰과 만료 시각으로 중복 실행을 제어하고, 서버가 만든 파일 목록만 Storage API로 삭제합니다. 재시도 간격은 늘어나며 최대 약 1시간 간격이고, 여러 파일 묶음이 남은 경우 빠르게 다음 묶음을 처리합니다. 작업자는 1분마다 필요 작업을 확인합니다.
실패 메시지 원문/이메일/사진 내용/키를 오류 기록에 넣지 않습니다. 관리자는 작업 참조 ID, 상태, 시각, 시도 수와 제한된 오류 코드만 보고 재시도를 예약할 수 있습니다. 5회 이상 실패하면 관리자 화면에 확인 필요 표시를 합니다. 자동 재시도를 위해 미완료 작업은 완료할 때까지 유지하며 조용히 버리지 않습니다. 장기 실패는 운영자가 해결해야 합니다.

3. 최소 삭제 처리 기록과 자체 백업 — 완료 후 30일
작업 참조 ID, 삭제 대상 계정 UUID, 요청/완료 시각, 삭제 범위 식별, 만료 시각 등 최소 처리 정보만 보관합니다. 파일 정리용 경로·단계 정보도 작업 기록과 함께 제거합니다. 이메일·비밀번호·레시피/메시지 본문·사진 사본은 자체 백업에 넣지 않습니다.
자체 백업 공간은 같은 Supabase 프로젝트의 비공개 retention-backups 버킷입니다. 서버가 Vault에 보관한 키로 최소 삭제 증빙을 AES-256 PGP 형식으로 암호화해 저장합니다. 앱 사용자·일반 관리자 브라우저는 파일/키를 읽거나 다운로드할 수 없습니다. 공개/서명 URL은 발급하지 않습니다.
업로드 후 다시 내려받아 SHA-256 해시를 확인해야 백업 검증 완료로 표시됩니다. 완료 후 30일에 만료되며, 만료 후 새 업로드/일반 작업 경로의 제공을 차단합니다. Storage API의 실제 삭제가 확인된 뒤에만 DB 처리 기록과 암호문을 제거합니다. 파일 삭제 실패는 다음 작업에서 다시 처리하고 관리자에게 만료 미정리 건수를 보여줍니다.
30일은 만료·파기 작업 기준입니다. 예약 실행·저장소 장애 때문에 물리적 삭제가 지연될 수 있으며, 지연을 숨기거나 무조건 정확한 시각까지 파기됐다고 표시하지 않습니다.

4. 신고·제재·이의신청
상세 신고 원문/콘텐츠 스냅샷/내부 증거/메모는 사건 종결 또는 최종 이의신청 검토 중 늦은 시점부터 30일 후 제거하거나 상세 내용이 삭제되었다는 표식으로 대체합니다. 만료된 사건 상세 열람 경로도 제한합니다.
계정·사건 ID, 조항·결론·제재 상태·필요 시각 등 최소 제재 이력은 90일 유지합니다. 삭제 대상자가 탈퇴할 때는 해당 사용자 원본 콘텐츠를 별도 신고 사본에 그대로 보관하지 않도록 정리합니다.
진행 중인 사건/이의신청은 처리 중 증거를 지우지 않으며 종결 시점부터 기산합니다. 현재 집행 중인 기간 정지/영구 정지의 최소 집행 정보는 종료·해제까지 필요합니다. 활성 제재를 이력 만료만으로 자동 해제하지 않습니다. 이후 필요 없는 최소 이력은 90일 기준으로 정리합니다. 원본 사용자 게시물 자체의 수명은 계정/콘텐츠 삭제 정책과 구분합니다.

5. 기타 앱 기록
원시 검색 이벤트: 발생 후 30일.
앱 내 제재 알림: 생성 후 30일.
레시피 댓글·내 댓글의 답글 알림: 생성 후 30일. 댓글 본문 사본 없이 계정/레시피/댓글 참조로 처리합니다. 숨김·차단 시 목록/읽지 않은 수에서 제외하고, 연결된 댓글·레시피·계정 삭제 시 함께 삭제합니다. 2026-10-16 추가.
앱 이메일 대기열: 발송 후 30일, 발송하지 못한 작업은 생성 후 30일. 아직 유효한 처리 임대는 중간에 지우지 않습니다.
보관 작업의 비식별 집계 실행 기록: 30일.
계정 ID를 포함하지 않는 레시피 단위 조회 통계는 개인 검색 기록과 구분합니다. 조회수를 떨어뜨리는 원시 행 무작위 삭제는 도입하지 않았습니다.

6. 제공자·메일함·기기 백업은 별도
위 30일 자동 파기는 Pickle이 직접 관리하는 DB 기록과 최소 삭제 증빙 버킷에 적용됩니다. Supabase의 인프라 DB 백업/PITR, Vercel 로그, Resend 발송 기록, Porkbun 전달 처리와 Gmail 문의 사본의 보관 설정을 바꿨다는 뜻은 아닙니다.
실제 제공자 플랜/로그·백업·메일함 설정을 별도로 확인해야 합니다. 이를 확인하기 전 외부 사본까지 무조건 30일 내 삭제된다고 안내하지 않습니다. 특히 일반 메일함의 휴지통 이동은 즉시 영구 삭제와 다를 수 있습니다. 다른 기기의 캐시/OS 백업도 앱에서 일괄 통제할 수 없습니다.
Supabase 기본 DB 백업은 Storage 사진 바이트를 포함하지 않습니다. 자체 retention-backups는 계정/사진 복구용 전체 백업도, 독립적인 전체 서비스 재난복구 백업도 아닙니다. 제공자 DB 복원 후에는 삭제된 계정을 다시 공개하기 전에 삭제 증빙과 최신 처리 상태를 확인·재반영해야 합니다.

7. 관리자 위치와 검증
/admin → Moderation → Data deletion, retention & backups.
접수/진행/재시도/완료, 백업 검증 대기, 만료 파일 미정리, 최근 파기 결과를 확인할 수 있습니다. 기존에 접수한 삭제 요청만 재시도할 수 있으며 임의의 다른 계정을 삭제하는 버튼은 없습니다.
DB의 롤백 테스트로 접근 권한·중복 임대·30일/90일 경계·이의신청·활성 제재 보호·암호화 최소 증빙·TTL을 확인했습니다. 저장 API는 모의 객체로 실패/재시도/다운로드 해시 검증을 확인했습니다. 배포된 작업자의 서버 연결과 예약 실행 성공도 확인했습니다.
2026-10-15 사용자 명시 승인 후 합성 최소 처리 기록 1건으로 운영 비공개 저장소의 암호화 업로드→다운로드 SHA-256 검증→만료 파기를 확인했습니다. 작업자 응답은 HTTP 200, 검증 1건·만료 삭제 1건·실패 0건이었고, 종료 후 삭제 작업·파일 작업·백업 객체는 모두 0건입니다. 실제 고객 계정·레시피·사진은 사용하거나 삭제하지 않았습니다. 만료 시각을 테스트용으로 앞당겨 파기 경로를 확인했으며, 실제 30일 경과를 기다린 테스트는 아닙니다.
