공급자/장소

- Resend: 서비스 이메일. 개인정보 전달 내역과 처리 국가·보관/삭제는 발송 계정 설정/계약에서 확인 필요.
- 웹 호스팅, 문의 메일 수신 업체: 운영자 답변 필요.
- 외부 동영상: YouTube 임베드, Instagram 외부 링크, 기존 영상 소스의 Vimeo/파일 재생 지원 코드가 있음. 사용자 재생/링크 실행 시 외부 요청이 발생할 수 있음. 실제 지원·사용 공급자를 최종 방침에 정리해야 함.

- 현재 사용자 업로드 레시피 이미지는 public URL로 표시. 프로필 숨김·차단·DB 행 제거가 이미 알려진 공개 파일 URL/다운로드 사본까지 회수하지는 못함.

탈퇴·삭제의 현재 상태와 위험
- delete-account는 관리자/공식 계정의 앱 탈퇴를 차단하고, 아바타/관련 채팅 이미지 정리 후 Auth 계정을 삭제하도록 되어 있음.
- DB의 recipes.author_id → profiles.id는 ON DELETE 처리가 없는 외래키. 검사한 Auth/Profile DELETE 트리거에 레시피 정리 단계가 없고 현재 함수에도 없음. 따라서 게시한 레시피가 있으면 탈퇴가 실패할 수 있음. 운영 환경에서 실제 계정을 지우는 테스트는 하지 않았음.
- 사진 정리는 계정 삭제보다 먼저 실행되므로, 뒤의 계정 삭제가 실패하면 계정은 남고 일부 사진만 지워질 수 있음. 이 순서도 수정 검토 대상.
- 계정 삭제 성공 시 프로필과 연결된 댓글/리뷰/좋아요/저장/팔로우/차단/메시지/동의 등은 외래키 CASCADE의 영향을 받음. 메시지는 송신자나 수신자 중 한 계정이 삭제되면 해당 행이 삭제됨. 정확한 최종 보장 범위는 수정 후 통합 테스트 필요.
- 일부 신고·제재 결정·감사 기록은 계정 참조가 NULL로 바뀌어도 남음. 스냅샷·본문·대상 ID 등에 개인정보가 남을 수 있어 완전 익명화라고 부를 수 없음. 댓글 신고처럼 CASCADE인 일부 기록도 있어 일관된 보관 원칙 정리가 필요.
- 검색 기록은 계정 ID가 NULL로 바뀌어 남을 수 있음.
- community_recipe_images의 물리적 파일 삭제는 현재 계정 삭제 함수에 없음. 게시물 삭제 RPC와 실제 파일 파기의 관계도 정해야 함.
- 알림/이메일의 공개 제거는 DB 상태 변경이며 증거·파일 영구 삭제가 아님. 이메일 제공자/메일함/백업에 이미 존재하는 사본은 별도 보관·삭제 절차 필요.
- 자동 보관 만료/파기 주기는 이 점검에서 확인하지 못함. 원하는 보관 기간을 먼저 쓰고 구현이 있다고 간주하면 안 됨.
